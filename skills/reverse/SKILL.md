# 逆向分析方法论

与 pwn（找漏洞打利用）不同，reverse 的目标是**理解程序到底在算什么**，
然后**取回它保护的凭据/flag**。本 skill 服务这类题。

## 〇、先定边界：静态 vs 运行时（别猜错战场）

动手前先回答 3 个问题，决定分析路径：

1. **flag 在哪一侧？** 纯本地二进制（运行后 stdout 出凭据）？
   还是有 HTTP/服务端（靶标吐凭据、二进制只是混淆）？
   - 纯二进制 → 本 skill
   - 服务端侧 → 先打服务，二进制作辅助
2. **静态够不够？** strings/反汇编能直接看到明文凭据 → 直接取。
   数据被加密/运行时才生成 → 必须动态（gdb/strace/hook）。
3. **最小可验证路径是什么？** 哪一条命令/哪一次运行能直接产出凭据？
   —— 不要无限泛化分析，先找"让系统给出答案"的最小输入。

铁律：**运行时真相 > 静态推测**。反汇编读不出"运行后才算出什么"，
只有让程序带着正确输入跑起来，输出才算数。

## 一、静态分析（先摸清结构）

```bash
file $BIN
checksec --file=$BIN          # ELF 保护状态（是否 PIE/stripped）
strings -a -n 4 $BIN | head   # 明文线索（Usage/flag 提示/路径）
readelf -S $BIN               # 段结构：.text/.rodata/.data/.bss 边界
objdump -d -M intel $BIN --start-address=0xXXX --stop-address=0xYYY
r2 -A $BIN -c "afl; pdf @main; q"     # 函数列表 + main 反汇编
```

`readelf -lW` 看 LOAD 段的 file offset——**flag 可能藏在段尾 overlay**，
文件大小 > 最后 LOAD 段尾 就是附加数据（`dd if=$BIN bs=1 skip=$OFF`）。

## 二、自定义 VM / 字节码解释器（重点）

很多逆向题内核是"自研执行机制"：一串字节码 + 一堆 handler。识别特征：
- 一个 `while(pc < len)` 主循环，`op = program[pc]` 后跳转到 handler 表
- **跳转表**（switch 或 `jmp [table + op*4]`）→ 把每个 opcode 对应 handler 列出来
- handler 里常有"读数据但丢弃"的迷惑操作——**别被带偏**

关键问题：
1. **程序循环几次、遍历什么数据？**（循环边界 = 数据长度）
2. **读进来的数据去哪了？** 如果读进 `eax` 后丢弃、输出是硬编码 `'.'`——
   **这是"被打码"的真实输出**：程序本意是输出数据，被篡改成固定字符。
3. **解密/转换缺在哪一步？** 把"读数据→组合→输出"链条补全，
   自己写 python 模拟器重建本应输出的值。
4. **每个 opcode 语义**：递进 pc、条件跳转、i++ 的索引——用 ipython 表格还原。

## 三、动态验证（运行时真相，别只信静态）

```bash
gdb -batch -ex "b *0x<入口>" -ex "run <args>" \
  -ex "x/32bx 0x<数据地址>" -ex "c" -ex "x/32bx 0x<数据地址>" $BIN
# 对比执行前后数据区：VM 可能在运行时改写密文/密钥
strace -f ./$BIN <args>       # 系统调用：看真正 write 了什么
ltrace ./$BIN <args>          # 库调用：看 putc/printf 参数
```

strace/ltrace 不可用时用 gdb 在 putc 下断点、`info registers` 看参数。

**hook 窄边界**（二进制带运行时校验时）：别 hook 一大堆。
定位"真正改变信任的那一步"——校验函数、加密 helper、密钥读取——
在其输入/输出各打一个点，记录明文、密文、key，重放接受的路径。

## 四、从密文/数据提取 flag

当 flag 藏在加密数据里：
1. 先确定长度与格式（`FLAG{...}`? 裸串?）——看题面 + 已解同类题
2. 找 key 与变换：读进数据的 handler 通常带 key（循环 `key[i&3]`）
3. **宁可提交试错**：算出候选后 `printf '%s\n' '候选值' >> FLAG` 让平台判——
   判错不等于白做，平台反馈收敛方向。不要因为"不确信"而迟迟不提交。
4. 常用尝试（按优先级）：XOR key、ADD/SUB key、key 字节序/补码、
   `op ^ 0x5a`（程序里常见魔数）、多段数据交织。
5. **把每一步锁成 证据→结论→路径**：命令原文+输出片段留档。
   结论必须能追溯到一次真实运行，而不是脑内推导。

## 五、patch 二进制（最后手段）

如果程序"本应"输出被保护值但被硬编码：`cp $BIN $BIN.patched`，
用 python 改字节（把 `mov edi,0x2e` 改成输出数据寄存器里的值），再运行看输出。

## 六、按证据面收敛（避免发散）

- 同一方向试 3+ 次没进展 → 换攻击面，不要执迷单一解码
- 静态推不动 → 动态；动态推不动 → hook/补丁；本 skill 走不通 → 退回服务端面
- 每轮只做"最小可验证的一步"：一次运行、一条命令、一个候选

## 要点
- **理解循环与数据流** > 盲目解密穷举
- 输出看似无意义（点/乱码）时，问：这是不是被打码的真数据？
- 动态调试对比数据区前后变化，常常一锤定音
- 算出的候选要提交试错，平台是最终裁判
- **运行时真相 > 静态推测**；最小可验证路径 > 泛化分析
